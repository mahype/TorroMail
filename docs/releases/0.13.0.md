# TorroMail 0.13.0

Accounts without a drafts folder can now create one after explicit account
consent, then use the existing draft and confirmed-send flow.

## New

- **Drafts folder consent:** the macOS account's **Special folders** section
  offers **Create a missing drafts folder**. It starts disabled for both new
  and migrated accounts. This permission is independent of drafting and
  sending; presets never enable it. The published policy key is
  `allow_create_drafts_mailbox`.
- **Namespace-aware creation:** TorroMail keeps explicit account mappings,
  prefers selectable `\Drafts` folders during automatic discovery, and falls
  back to known names using the server's hierarchy delimiter. If consent is
  granted and no suitable folder exists, it creates Drafts under the personal
  IMAP namespace, uses CREATE-SPECIAL-USE when available, checks LIST and
  SELECT, subscribes when possible, and remembers the mapping for this account.
- **Safe draft retries:** `mail_create_draft` accepts an `idempotency_key`.
  Reuse it with the same contents after a failure or MCP restart; key renewal
  for the same paired client also preserves the operation. A new key allows
  an intentional second identical draft. Without a key, identical contents
  are deduplicated for that account and client.

## Fixed

- Draft creation returns a `draft_id` only after fetching and verifying the
  complete stored MIME and `\Draft` flag. Recipients and attachment bytes
  are preserved. An uncertain APPEND is reconciled by Message-ID and cannot
  be blindly repeated. Concurrent MCP processes coordinate through private,
  durable account metadata and an operating-system file lock.
- Draft setup and storage failures keep JSON-RPC code `-32000` and expose an
  actionable `error.data.reason`: missing folder, refused creation,
  nonselectable folder, unavailable namespace, refused storage, or uncertain
  storage. Explicit mappings are never silently replaced.
- Draft audit entries contain only recipient and attachment counts. They no
  longer retain recipients, subjects, or attachment filenames. State metadata
  stores only hashes and mailbox names, never message contents or credentials.
- MCP initialization reports the actual workspace version.

## Verification and boundaries

The disposable Dovecot integration test covers root `/`, `INBOX.` and
`Personal:` namespaces, actual CREATE/APPEND/FETCH, a lost APPEND acknowledgement,
restart recovery, concurrency, attachments, recipient preservation, client key
renewal, and confirmation followed by delivery to a local SMTP sink. CI runs
it in addition to the Rust and Swift contracts.

Send permission and the existing confirmation handshake remain required.
Sent, Archive, Junk, and Trash still require existing selectable folders.
An account whose only folders are INBOX and Trash therefore also needs a Sent
folder or explicit suitable mapping before SMTP submission. This release only
authorizes automatic creation of Drafts. No real-recipient test mail was sent.

If an uncertain draft remains invisible on the server, TorroMail stops safely;
inspect the server before intentionally beginning a new operation. The local
build's signing, notarization and artifact checks are documented in
[the verification report](https://github.com/mahype/TorroMail/blob/v0.13.0/docs/verification/2026-10-09-drafts-folders.md).

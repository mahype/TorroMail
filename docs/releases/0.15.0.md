# TorroMail 0.15.0

Servers with a certificate no authority vouches for can now be connected — a
local Proton Mail Bridge, a home server, a certificate for another name. And a
failed connection check now says what actually failed instead of blaming the
password for everything.

## Changed

- **Trust a server certificate:** when verification refuses a certificate,
  account setup shows a dedicated step with a clear warning, the server, the
  reason (self-signed, expired, not yet valid, wrong name) and the SHA-256
  fingerprint. **Trust and Add** remembers the certificate for that account
  and checks again. The decision is permanent and covers IMAP and SMTP;
  TorroMail asks again only if the certificate changes. A changed certificate
  turns the account red at once, and the account detail offers the same
  decision with **Trust This Certificate**.
- **How trust works:** normal verification against the bundled Mozilla roots
  always runs first; a trusted fingerprint is consulted only when it fails, and
  handshake signatures are still checked against the certificate's key. The
  policy document carries the fingerprints as `trusted_certificates` in both
  connection blocks; `state.json` stores them as `trustedCertificates`. A
  malformed list fails closed.
- **Separate error messages in setup:** a rejected login, an unreachable
  server, a failed encryption (SSL/TLS vs. STARTTLS mixed up) and anything
  else each get their own sentence. Only a spoken refusal mentions the
  password; the server fields open where they are the fix.
- **New health outcome `untrusted`:** written by the server, the app and the
  terminal surface. It turns the status dot red immediately, like a refused
  login, and is never reported as a password problem. Assistants calling a
  tool against such an account get
  `certificate not trusted: server=… reason=… sha256=…`.

## Known limits

- The connection check proves IMAP only. A server presenting a different
  certificate for SMTP than for IMAP shows that on the first send. Proton Mail
  Bridge uses the same certificate for both.
- The terminal surface (`torromail`) reports an untrusted certificate as its
  own message but cannot trust it yet; use the app for that decision.

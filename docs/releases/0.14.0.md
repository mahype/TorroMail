# TorroMail 0.14.0

SMTP submission no longer requires an IMAP connection or a working Sent
folder. A mailbox failure after SMTP acceptance affects only the Sent copy.
Existing send permissions, client account grants and confirmation requirements
remain in force.

## Changed

- **Independent outcomes:** confirmed sends return a stable `operation_id`,
  `submission_status` (`accepted`, `not_accepted`, `unknown`) and
  `sent_copy_status` (`saved`, `pending`, `provider`, `skipped`). Before SMTP
  acceptance the copy status is `not_applicable`. Acceptance is the final 250
  after DATA, not confirmation of recipient delivery
  ([RFC 5321](https://www.rfc-editor.org/rfc/rfc5321#section-4.1.1.4)).
- **Durable submission journal:** owner-only spool files hold the exact MIME
  and envelope, including Bcc, without storing credentials. Synced atomic
  checkpoints and per-operation OS locks prevent concurrent or repeated
  confirmations from submitting again. An interrupted `submitting` operation
  becomes `unknown`; it never automatically resubmits. SMTP and Message-ID do
  not provide a general exactly-once guarantee.
- **Copy-only recovery:** accepted operations resume Sent-copy work after a
  restart and every 60 seconds while an MCP server runs. Tagged APPEND refusals
  can retry the copy. Lost APPEND acknowledgements reconcile the original
  mailbox using Message-ID, exact MIME and the Seen flag. An invisible,
  ambiguous copy stays pending. Recovery never calls SMTP.
- **Configurable copies:** account → **Special folders** → **Sent copies for
  MCP messages** offers **Save in the IMAP Sent folder**, **The provider saves a
  copy**, and **Do not save an additional copy**. Existing accounts migrate to
  IMAP storage. The policy key is `sent_copy_strategy` (`imap`, `provider`,
  `none`). This setting avoids an additional copy when the provider already
  files sent mail.
- **Shared special-folder management:** Drafts and Sent use explicit account
  mappings, SPECIAL-USE/XLIST/common-name detection, selectable folders and the
  advertised personal namespace/delimiter. Sent creation needs separate
  `allow_create_sent_mailbox` consent, off by default, and verifies LIST/SELECT
  afterwards. An invalid manual mapping is reported and retained.
- **Local sendable drafts:** `mail_create_draft` accepts `storage: "local"` to
  persist a draft without IMAP. Default `storage: "imap"` retains the existing
  server-draft flow. Both require the draft right. IDs and idempotency keys
  survive restart; changed sender, recipients, body, MIME or attachments
  invalidate the approved fingerprint. The locally approved snapshot is
  immutable; changing an IMAP draft does not change this snapshot.
- **Shared GUI/MCP service:** the app now lists durable send preparations and
  implements review, approval and rejection through the same Rust service as
  MCP. The preview includes sender, full envelope, subject, body and attachment
  summaries. GUI approval also rechecks the originating client's account grant.
  The existing five-minute approval TTL remains. Move/delete preparations
  remain session-local.

## Authorized live test

One clearly labelled test message, including a 49-byte test attachment, was
submitted from an explicitly authorized account to the user-specified recipient
with the new signed binary. Account and recipient addresses are omitted from
the public report.

- SMTP: `submission_status: "accepted"`.
- Sent copy: `sent_copy_status: "saved"`, in the server-discovered `INBOX.Sent`.
  The production copy path verified exact MIME and the Seen flag; a live search
  found the stored copy.
- Repeated confirmation returned the same operation without another SMTP send.
- After installation, a fresh 0.14.0 process again returned that same accepted,
  saved operation without sending again.
- The user subsequently confirmed that the test message arrived. This is a
  separate live-test observation; SMTP acceptance alone remains no guarantee
  of recipient delivery.

Local, credential-free evidence is retained in `.codex/test-results/` and is
excluded from the public repository. Pre-release validation used a locally
signed arm64 development build. Distribution packages, notarization, DMG smoke
checks and the signed Sparkle appcast are produced by the release workflow.
Existing MCP client processes must restart to load the updated binary at their
configured path.

## Operational limits

Send spool MIME is retained in private `send-state/`, separately from the read
cache. Lost SMTP acceptance and invisible ambiguous APPEND outcomes require
inspection; TorroMail deliberately refuses a blind retry that could duplicate
mail. Folder creation remains a convenience, not a prerequisite for SMTP.
